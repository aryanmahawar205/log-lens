# Sigma Rules Management in LogLens

LogLens natively acts as a consumer of standard, externally-maintained Sigma rules. You can drop hundreds of rules into the proper directories and LogLens will automatically parse, translate, and execute them during the security analysis phase.

## Directory Layout

Sigma rules should be placed in the `backend/rules/sigma` directory. The engine recursively discovers all valid `.yml` and `.yaml` files, meaning you can organize rules into any subdirectories you see fit. A common organizational pattern is:

```
backend/rules/
  sigma/
    official/    # Standard rules downloaded from official Sigma repositories
    custom/      # Custom rules specific to your environment
    experimental/ # Experimental rules
```

## Rule Discovery

When the Sigma engine loads rules (either on startup or when manually reloaded), it recursively scans the base directory `rules/sigma` and subdirectories.

The loading process is robust:
- Valid rules are successfully loaded.
- Duplicate rule IDs are ignored and marked as duplicates.
- Rules missing the required `detection` block are skipped and tracked as ignored.
- Invalid YAML files are tracked as failed rules.
- A failure in one rule does not prevent the loading of others.

## Supported Sigma Features

The current LogLens Sigma engine translates basic Sigma syntax into DuckDB SQL. It currently supports:

- **Logical Operators:** `and`, `or`, `not`
- **Modifiers:** `contains`, `startswith`, `endswith`
- **Lists and Selections:** Converts selections into lists of OR clauses, and combines maps with AND logic.
- **Wildcards:** Keyword searching and matching keys.

If a rule relies on features not currently supported, it may generate unexpected SQL or silently fail to match logs.

## Adding Rules

1. Obtain valid Sigma rule YAML files.
2. Drop them into any subdirectory under `backend/rules/sigma/` (e.g. `rules/sigma/custom/my_rule.yml`).
3. Reload the Sigma engine (see below).

## Removing Rules

1. Delete or move the `.yml` file out of the `backend/rules/sigma/` tree.
2. Reload the Sigma engine.

## Reload Workflow

To make LogLens aware of the new, updated, or removed rules without restarting the application:

1. **API:** Send a `POST` request to `/api/v1/security/rules/reload`
2. **UI (Future feature):** Click the "Reload Rules" button in the System Diagnostics page.

## Validation Workflow

To validate your rules are loaded and functional:

1. Add your new Sigma rule.
2. Trigger a reload using the API.
3. Open the **System Diagnostics** page in the UI.
4. Check the **Sigma Engine** diagnostics card. The "Total Discovered" and "Loaded Rules" should increment.
5. In the **Sigma Rule Inventory** search for your newly added rule and verify its "Load State" is loaded.
6. Upload a log that matches the rule signature using the Dashboard.
7. Navigate to **Security Analytics** > **Findings** and verify the matching record generated a security finding.

## Troubleshooting

- **Rule not appearing in Inventory:** Check if it was marked as a duplicate (duplicate rule ID), ignored (missing `detection` field), or failed (invalid YAML). This information is visible in the System Diagnostics.
- **Rule generates no findings:** Verify the translated SQL generated by the engine accurately represents your rule, and ensure the uploaded log data actually matches the conditions. Use the `query_string` or `url` fields to test match logic.
